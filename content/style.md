# Writing style

Stefan's direction from 2026-10-25. Read this before drafting or editing any post.

## Voice

- First person: my perspective, my experience, what I intended and what happened.
- Lab notes, not essays. Say what I did, what I found, what I changed, and what is still open.
- Clear and plain. No prose for its own sake, no build-up, no flourishes, no clever framing.
- Short sections with plain headings. Use lists where the content is a list, and code where the reader would type it.
- Facts I can show: commands, settings, before and after. Every claim from outside my own work gets a source.

## Titles

Stefan, 2026-10-29: plain titles in the form "Securing <what>", naming the actual tools, so people searching for them find the post. No clever titles.

- Securing a Zensical Blog on GitHub Pages
- Securing Build and Deploy with GitHub Actions
- Securing DNS with Cloudflare and Namecheap

The slug is the title in lowercase with dashes.

## Every post starts with a brief

Fill in the `brief` block in the front matter before writing. It isn't published.

- **goal:** what the post should achieve.
- **purpose:** why I'm writing it now.
- **reaction:** what I want readers to do or say afterwards.
- **intent:** the kind of post it is, for example lab notes, a checklist, or a request for feedback.

If the draft doesn't serve the brief, cut it.

## What not to write about

- Small things that went nowhere. For example, an upstream bug that was already fixed and that I didn't report isn't a post.
- Giving back to open source is a topic only when we actually give something back: a fix, a security finding, or working with an author.
- Anything on the never-share list in backlog.md.
