# Securing a Blog That Has Nothing to Lose

<!-- DRAFT for Stefan. Facts marked VERIFY need a source check before publishing.

This blog has been quiet since April 2024. Before writing anything new, I wanted to answer a simple question: what can actually go wrong with a static site on GitHub Pages?

My first answer was "nothing much". There's no server, no database, no login. Everything on it is public anyway.

<!-- more -->

That answer is an assumption, and checking assumptions is my day job. So I treated this blog like any other application: I looked at the domain, the hosting, the build, the deploy and the browser. Then I pointed an AI security review at the repository and at the package that builds it.

Here is what I found, and what I changed.

## What a static site can lose

A static site has no data to steal. It does have three things worth protecting:

- **The domain.** Anyone who controls what `thoughtson.ai` serves can publish under my name, phish readers or serve malware.
- **The build.** The site is generated by a pipeline. Whatever runs in that pipeline can change every page.
- **The reader's browser.** Every third-party script on the page runs with the page's privileges.

## The domain and DNS

The domain is registered at Namecheap, with DNS on Cloudflare. The apex redirects to `www`, and `www` is a CNAME to GitHub Pages. That's a standard setup, and it had four gaps:

1. **The custom domain wasn't verified with GitHub.** Without verification, if Pages is ever disabled while the CNAME still points at GitHub, someone else can claim the domain for their own Pages site. Verifying the domain on your GitHub account closes that. <!-- VERIFY against the GitHub docs page "Verifying your custom domain for GitHub Pages" -->
2. **HTTPS wasn't enforced.** `http://www.thoughtson.ai` served the page instead of redirecting. It's one checkbox.
3. **No CAA records.** CAA records tell certificate authorities which of them may issue for your domain. GitHub Pages uses Let's Encrypt; Cloudflare uses its own set. <!-- VERIFY Cloudflare's CAA behaviour for proxied hosts before recommending exact records -->
4. **Email I don't send.** The domain had an SPF record left over from email forwarding, but no mail server and no DMARC. A domain that never sends mail should say so: `v=spf1 -all` and a DMARC policy of `p=reject`. Otherwise anyone can send convincing mail "from" it.

DNSSEC was also off. It's a small step at most registrars, once DNS is on a provider that signs.

## The build

The old build installed five packages without versions, on every push:

```text title="requirements.txt (before)"
mkdocs-material
mkdocs-material[imaging]
mkdocs-minify-plugin
mkdocs-rss-plugin
pymdown-extensions
```

That means whatever was newest on PyPI at build time ran with write access to the site. Now every package in the tree is pinned with a hash, and new releases wait seven days before I take them:

```bash
uv pip compile requirements.in --generate-hashes --exclude-newer 2026-10-18 -o requirements.txt
pip install --require-hashes --no-deps -r requirements.txt
```

The cooldown matters because most malicious releases are found and pulled within days. <!-- VERIFY: cite a source for how quickly malicious npm/PyPI releases get removed --> Waiting a week costs nothing for a blog.

While pinning, something interesting showed up. Two plugins, `mkdocs-redirects` 1.2.3 and `mkdocs-rss-plugin` 1.18, had started depending on `properdocs`, a fork of MkDocs created in March 2026. That's very likely a legitimate community fork, since MkDocs itself is no longer maintained. But a patch release that adds a new upstream project to your build is exactly the change you want to notice rather than absorb. I stayed on the releases that don't need it, for now.

The bigger picture: Material for MkDocs, the theme this blog uses, has been in maintenance mode since November 2025. Its authors moved on to [Zensical](https://zensical.org/), which reads the same configuration. A pinned build is fine for today; the migration is on the list.

## The deploy

The old workflow ran `mkdocs gh-deploy --force` with write access to the whole repository, using actions pinned only by tag. A tag can be moved to point at different code.

The new workflow:

- pins every action to a commit SHA, with Dependabot proposing updates after a 7-day cooldown;
- builds every pull request with read-only permissions;
- publishes only from `main`, through GitHub's Pages deploy action, with `pages: write` and `id-token: write` and nothing else;
- doesn't leave the checkout's token on disk (`persist-credentials: false`).

## The browser

Two third-party scripts run on these pages: Google Analytics, behind a consent banner, and Giscus for comments. Both are reasonable. Both are also code I don't control running on my domain.

## The checklist

If you run a static site on GitHub Pages:

- [ ] Verify your custom domain on your GitHub account.
- [ ] Enforce HTTPS.
- [ ] Add CAA records for the CAs you actually use.
- [ ] Publish `v=spf1 -all` and DMARC `p=reject` if the domain sends no mail.
- [ ] Turn on DNSSEC.
- [ ] Pin build dependencies with hashes, and wait a few days before taking new releases.
- [ ] Pin actions to commit SHAs, and give the deploy job only `pages: write` and `id-token: write`.
- [ ] Know every third-party script on your pages, and why it's there.

None of this took long. The point is that "it's just a static site" was true for the data, and not true for the domain, the build or the readers.
